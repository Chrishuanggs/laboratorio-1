Concept

What is a realm?

A realm is an isolated space inside Keycloak with its own users, roles, applications (clients), login settings and signing keys. Nothing is shared between realms. A user in realm A doesn't exist in realm B, and a token signed by realm A is rejected by an API that trusts realm B.

RealmOne apartmentIts own residents (users), its own keys (signing keys) and its own house rules (roles).
master realmThe building manager's officeUsed only to administer Keycloak itself. Never put application users here.
Our APIA guest who trusts one apartmentissuer-uri in application.yml points at /realms/veterinaria, so only its tokens are accepted.

Part 1 of 5

Realm settings

The first lines name the realm and set rules that apply to everything inside it.

{
  "realm": "veterinaria",
  "enabled": true,
  "sslRequired": "none",
  "accessTokenLifespan": 900,
  "roles": { … part 2 and 3 },
  "clients": [ … part 4 ],
  "users": [ … part 5 ]
}
realm "veterinaria"
The realm's unique name. It becomes part of every URL, for example http://localhost:8180/realms/veterinaria. That URL is also the issuer (iss) written into every token. Connects to: spring.security.oauth2.resourceserver.jwt.issuer-uri. If the names don't match, the API rejects every token with 401.
enabled true
Turns the realm on. A disabled realm refuses all logins and token requests.
sslRequired "none"
Whether Keycloak demands HTTPS. Options: "all", "external" (the default: HTTPS for anything not from localhost) and "none". Why "none" here: requests from your laptop reach Keycloak through Docker's network, so Keycloak sees them as external and answers "HTTPS required". Use "none" only for local demos. In production, always use HTTPS.
accessTokenLifespan 900
How long an access token is valid, in seconds: 900 s = 15 minutes. After that the API answers 401 and the client must get a new token. Trade-off: short-lived tokens limit the damage if one leaks, and role changes take effect sooner. A changed role only shows up in tokens issued after the change.
Part 2 of 5

Permissions: client roles

Keycloak calls them client roles because they belong to one application. We use them as fine-grained permissions, one per action the API can perform.

"roles": {
  "client": {
    "persistencia-api": [
      { "name": "perro:leer",
        "description": "Consultar perros" },
      { "name": "duenno:leer", … },
      { "name": "duenno:escribir", … },
      { "name": "duenno:eliminar", … },
      { "name": "chat:usar", … }
    ]
  }
}
roles.client
A map from a client's clientId to that client's roles. The key "persistencia-api" must match a client defined in part 4.
name "duenno:eliminar"
The permission's identifier. It travels in the token and Spring checks it with @PreAuthorize("hasAuthority('duenno:eliminar')"). Naming convention: resource:action keeps permissions easy to read and to group. Keycloak doesn't care about the format. It's our own convention.
description
Human-readable text shown in the admin console. It has no effect on security.
Where it lands in the token
resource_access.persistencia-api.roles. KeycloakJwtConverter reads that list using the keycloak.client-id property.
Part 3 of 5

Roles: composite realm roles

Realm roles describe who someone is. Each one is composite, which means it bundles a set of permissions. Assigning VETERINARIO to a user gives them every permission inside it.

"roles": {
  "realm": [
    {
      "name": "VETERINARIO",
      "description": "Personal de la veterinaria…",
      "composite": true,
      "composites": {
        "client": {
          "persistencia-api": [
            "perro:leer", "duenno:leer",
            "duenno:escribir", "chat:usar"
          ]
        }
      }
    },
    { "name": "ADMIN", … },
    { "name": "CLIENTE", … }
  ]
}
roles.realm
Roles that belong to the whole realm, not to one application. Any client in the realm can see them.
name "VETERINARIO"
The role's identifier. Our converter adds the prefix, so it becomes the Spring authority ROLE_VETERINARIO, checked with hasRole('VETERINARIO') or @Secured("ROLE_VETERINARIO"). Lands in the token at: realm_access.roles.
composite true
Marks the role as a container of other roles. Without it, composites is ignored.
composites.client.persistencia-api
The permissions this role includes. When the user logs in, Keycloak expands them and writes them into the token as if they had been assigned one by one. The payoff: to let VETERINARIO delete, add duenno:eliminar here or in the admin console. No Java changes and no redeploy.
composites.realm (not used)
A role can also include other realm roles, for example ADMIN including VETERINARIO. We left it out on purpose so the demo shows that roles are not hierarchical by default: ana (ADMIN) gets 403 on /demo/veterinario.
Part 4 of 5

The client: our application

A client is any application registered with Keycloak, such as a web frontend, a mobile app or an API. Its settings decide how it may obtain tokens.

"clients": [
  {
    "clientId": "persistencia-api",
    "name": "API de Persistencia (Spring Boot)",
    "enabled": true,
    "publicClient": true,
    "directAccessGrantsEnabled": true,
    "standardFlowEnabled": true,
    "redirectUris": [
      "http://localhost:*",
      "https://oauth.pstmn.io/v1/callback"
    ],
    "webOrigins": ["+"],
    "fullScopeAllowed": true
  }
]
clientId "persistencia-api"
The identifier the app sends when asking for a token (client_id=persistencia-api). It's also the key under resource_access in the token, and the value of keycloak.client-id in application.yml.
name
Display name for the admin console and the login screen. Cosmetic.
enabled true
A disabled client can't get tokens.
publicClient true
Public = no client secret. That's right for code that runs on the user's device (a browser SPA or mobile app), where a secret can't be kept hidden. A confidential client (false) has a secret and is used by back-end services. Here: public keeps the demo to a single curl without managing secrets.
directAccessGrantsEnabled true
Allows the password grant: the client sends username and password straight to the token endpoint. This is what http/seguridad.http and the curl examples use. Production: avoid it. OAuth 2.1 removes this grant because the app gets to see the user's password.
standardFlowEnabled true
Allows the Authorization Code flow: the app redirects the user to Keycloak's login page and receives a short code that it exchanges for tokens. This is the recommended flow for real web and mobile apps, used together with PKCE.
redirectUris
Where Keycloak may send the user back after logging in with the Authorization Code flow. Any other URL is refused, which stops attackers from stealing codes. Here: any localhost port (for a local frontend) and Postman's OAuth callback. In production, list exact URLs. Never use wildcards.
webOrigins ["+"]
CORS origins allowed to call Keycloak from a browser. "+" means "the same origins as the redirect URIs".
fullScopeAllowed true
Puts all of the user's roles into this client's tokens. With false, you choose which roles may appear, which keeps tokens smaller and follows least privilege.
Part 5 of 5

Users

Three demo accounts, one per role. Each gets a password and a realm role, never a permission directly.

"users": [
  {
    "username": "victor",
    "enabled": true,
    "email": "victor@veterinaria.local",
    "emailVerified": true,
    "firstName": "Victor",
    "lastName": "Veterinario",
    "credentials": [{
      "type": "password",
      "value": "victor123",
      "temporary": false
    }],
    "realmRoles": ["VETERINARIO"]
  },
  { "username": "ana", … "realmRoles": ["ADMIN"] },
  { "username": "carla", … "realmRoles": ["CLIENTE"] }
]
username "victor"
The login name. It appears in the token as preferred_username, and our converter uses it as Spring's authentication.getName(). Used by: @PreAuthorize("#username == authentication.name or hasRole('ADMIN')") on /demo/perfil/{username}.
enabled true
A disabled user can't log in. It's the quickest way to block someone without deleting them.
email, emailVerified, firstName, lastName
Profile data, included in the token as email, name and so on. Don't skip them: Keycloak's user profile requires these fields. If they're missing, the login fails with "Account is not fully set up" because the user has to complete their profile first.
credentials
The user's password. type: "password" is a normal password, and value is the plain text that Keycloak hashes on import. temporary: false means the user doesn't have to change it on first login. With true, the password grant fails until they do.
realmRoles ["VETERINARIO"]
The realm roles assigned to the user. Through the composite role, victor inherits perro:leer duenno:leer duenno:escribir chat:usar.
clientRoles (not used)
Keycloak can also assign permissions to a user directly. We avoid it on purpose: managing access through roles scales better than managing it one user at a time.
Putting it together

From the file to a 200 or a 403

What happens to victor's configuration when he logs in and calls DELETE /api/v1/duenno/5.

1 · Keycloak writes the token

Roles from the user, permissions expanded from the composite role.

{
  "iss": "http://localhost:8180/realms/veterinaria",
  "preferred_username": "victor",
  "realm_access": {
    "roles": ["VETERINARIO", …]
  },
  "resource_access": {
    "persistencia-api": {
      "roles": ["perro:leer",
        "duenno:leer", "duenno:escribir",
        "chat:usar"]
    }
  }
}
2 · Spring translates it

KeycloakJwtConverter turns the claims into authorities. Check them yourself at GET /api/v1/demo/yo.

// authorities
ROLE_VETERINARIO   ← realm_access
perro:leer         ← resource_access
duenno:leer
duenno:escribir
chat:usar
3 · The annotation decides

The authority isn't in the list, so Spring answers 403 Forbidden before the method runs.

@PreAuthorize("hasAuthority('duenno:eliminar')")
@DeleteMapping("/{id}")
public ResponseEntity<Void> delete(...)

// victor → 403   ana → 204 / 404
How the file gets loaded

Import on startup

kc.sh start-dev --import-realm
Run by docker/keycloak/start.sh, the container's entrypoint. On startup Keycloak reads every .json in /opt/keycloak/data/import, where our file is mounted read-only.
The master realm is not in this file
master is created by Keycloak itself, so it keeps the default sslRequired: "external" and the admin console would answer "HTTPS required". After startup, start.sh runs Keycloak's admin CLI (kcadm.sh update realms/master -s sslRequired=NONE) from inside the container, where the request counts as local.
Only if the realm doesn't exist
If veterinaria already exists, the import is skipped. Changes made in the admin console survive a restart but disappear when the container is recreated, because dev mode keeps no volume.
Reset to this file
docker compose -f docker/docker-compose.yml up -d --force-recreate keycloak
Export your changes
Admin console → Realm settings → Action (top right) → Partial export. That's how you'd turn changes made by clicking into a file like this one.

Never in production: plain-text passwords in a JSON file, sslRequired: "none", the password grant and wildcard redirect URIs. They're here so the demo runs on a laptop with one command.
